# Open Digital Rights Enforcement Framework (ODRE): from descriptive to enforceable policies

- **Paper:** Andrea Cimmino, Juan Cano-Benito, Raúl García-Castro (Ontology Engineering Group, Universidad Politécnica de Madrid)
- **arXiv:** [2409.17602](https://arxiv.org/abs/2409.17602) (26 Sep 2024, cs.CR); Computers & Security 150:104282 (2025)
- **Implementations:** [pyodre](https://pypi.org/project/pyodre/) (Python + Jinja2); [odre-java](https://github.com/ODRE-Framework/odre-java) (SPARQL + Freemarker), Maven `io.github.odre-framework/odre-core`; time extension https://w3id.org/def/odre-time; Zenodo https://zenodo.org/records/13735971
- **Source extract:** `research_papers/extracted/2409.17602.txt` (21 pages)

## Core Problem & Motivation

ODRL is a **descriptive** W3C ontology with **no enforcement specification**. Data-space initiatives need a mechanism that (i) checks constraints and (ii) invokes actions. Additional practical holes:

- **Stone-written conditions** leak private values (geofence polygons, API tokens) and cannot track live GPS.
- Abstract operands/actions (`read`, `spatial`) admit incompatible implementations.
- Binary operators cannot express N-ary predicates (two WGS84 points + 1 km threshold).
- Operands/actions are 0-ary (no timezone input to `dateTime`).
- No vocabulary for sync vs async enforcement or *who* evaluates / performs actions.

**Gap filled:** classify policies by **behavioural language layers**, give an implementation-agnostic **enforcement algorithm**, and ship Python and Java engines with extension points—without translating ODRL into XACML/MYDATA (lossy).

## Architecture / Formalism

Chomsky / Model–View inspiration: descriptive RDF (View) vs languages that inject behaviour (Model).

### Policy levels (must preserve ODRL lexicon for usage conditions)

| Level | Language | Role | Output of “enforcement” of this layer |
|---|---|---|---|
| **∅** | RDF + ODRL (descriptive) | Vocabulary only | — |
| **A** | Interpreted (Python, SPARQL, …) | Couple ontology terms to functions; **only mandatory layer** | **Usage Decision** |
| **B1** | Interpolated (Jinja/Freemarker vars) | Inject request/runtime values | A-level |
| **B2** | Templated (control flow, `#assign`) | Data handling **inside** policy | B1 |
| **C** | Coded (Python/Java functions passed in) | External I/O (HTTP GET weather, …) | B2/B1 |

Usage Decision \(D\): set of \((a, V)\) if action supported and performed, or \((a, a)\) to **notify a third party** if unsupported/abstract.

**Hard rule:** usage restrictions must remain ODRL (or ontological extensions). Interpolation/templates/code **only** for dynamic data and privacy hiding—not for encoding extra constraints.

### Algorithm 1

Inputs: \(P^*\), data map \(M\), function map \(F\). Output: \(D\).

```
D ← ∅
PA ← reduce(P*, M, F)          # B/C → A
for rid in rules(PA):
    CR ← constraints(PA, rid)  # {(operator, left, right)}
    PI ← transformConstraints(CR)
    d  ← evaluate(PI)
    if d:
        a ← action(PA, rid)
        if supported(a):
            D ← D ∪ {(a, perform(transformAction(a)))}
        else:
            D ← D ∪ {(a, a)}   # notify third party
```

`reduce` substitutes `[=var]` / template procedures. Python `transformConstraints` concatenates binary functions with `and` and XSD→Python casts; SPARQL uses `BIND` + `AND` and native `>` / `==` where possible (`fnc:now`, `fnc:media` as extensions). `evaluate` = Python `eval` or a SPARQL engine with extension functions.

**Synchronous only** in this paper.

### Extension recipe

1. Add ontology terms (NeOn-style). Example: `otime:time`, `otime:between`; demo action `dummy:read`.
2. Implement functions in the interpreted language and couple them to those terms.
3. Optionally add template procedures / coded functions for data handling.

## Evaluation & Benchmarks

24 policies × 24 unit tests in **each** of pyodre and odre-java:

- 6 constant ⋈ constant (`lt, lteq, eq, neq, gt, gteq`)
- 6 `odrl:dateTime` ⋈ constant
- 6 `otime:time` ⋈ constant
- 1 `otime:between`
- 1 `dummy:read`
- 4 templated interpolation (vars/functions)

Timing: each test **15 runs**, drop 5 warm-up, average. **All enforcements < 0.03 s**. Java generally faster than Python except `test_extension_action` (Java streams on HTTP). Coverage of ODRL operators in engines: the six numeric/string comparisons + `dateTime` + the time extension—**not** set operators, not full IM.

## Limitations & Failure Modes (authors’ Section 3.2)

1. **ODRE bad practice:** mixing RDF with templates can hide constraints in code, yield “different-looking same policies,” and destroy comparability (directly at odds with Salas comparison/normalisation).
2. **Sync vs async:** ODRL cannot label which policies must be continuously monitored; Algorithm 1 is sync-only.
3. **Abstract ODRL terms:** `read` as API access vs returning payload vs physical reading—extend the ontology rather than burying meaning in Jinja.
4. **Binary predicates only;** N-ary needs ontology change, not a third “operand” namelessly.
5. **0-ary operands/actions;** nested operands future.
6. **Stone-written constants** leak secrets; ODRE interpolation is the sanctioned fix **without** leaving ODRL for the actual condition.
7. **Responsibilities unspecified:** who evaluates, who performs, who supplies `spatial`, who may trigger enforcement.
8. Related-work warning: translating to XACML/MYDATA cannot cover full ODRL or future profiles.

No SHACL validation, no deontic conflict theory, no KB-backed `isA`/`isPartOf`. Constraints of a rule are **implicitly conjoined** (`and`).

## Key Takeaways for an NL-to-ODRL system

1. Generation should emit **A-level-valid ODRL**; interpolation holes (`[=requestToken]`) are an **enforcement-time** concern, not an LLM target—or, if generated, must be flagged as B1 and never as “complete policy graphs” for SHACL/SMT.
2. Implement `transformConstraints` / `transformAction` as the **stable interpreter API**; Python and SPARQL are both sufficient if functions are coupled to ontology IRIs.
3. Extend **ontology + interpreter together** (time, geo); do not encode geo-contains as template logic.
4. Usage Decision’s \((a,a)\) branch is the hook for human/org duties ODRE cannot execute (aligns with UFO-L Power/Duty split: engine vs party).
5. Sub-30ms numeric/dateTime enforcement is cheap enough to sit **after** SMT conflict checks.
6. Prohibit generators from putting control-flow (`#if`, `#list`) that implements extra usage conditions—violates the paper’s own correctness criterion and breaks formal comparison.
7. ODRE is **access-control-ish constraint evaluation + action dispatch**, not monitoring of Salas event logs; connect by treating a granted Usage Decision as a candidate event to append and then evaluate 2509.05139 queries.
